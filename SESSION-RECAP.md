Verified with a real send landing in Gmail's Sent folder and a real undo that never dispatched.
- **S3** — Frontend's first real backend wiring: Connect screen, `frontend/lib/emptify/api.ts` (the fetch wrapper + `X-Role` attachment), all 3 accounts connecting/reconnecting through the real UI, debounced internal-domains PATCH.
- **S4** — Voice profile builder (`backend/app/services/voice.py`): pulls 90 days of Sent mail per account, noise-filters (forwards/auto-responses/short replies), splits by recipient domain into pooled client/internal profiles, extracts 6 traits + a default note via one forced-tool-use Anthropic call per mode. Rebuilding a profile only sets the default note the *first* time — later rebuilds never overwrite notes the user edited (explicit product decision, see S4 section in the dev plan).
- **S5** — Real inbound triage (`backend/app/services/triage.py`): incremental Gmail Inbox sync (capped at 20 new messages/account/call, dedup by Gmail `threadId`, `last_sync` only advances when the whole backlog was processed), one Anthropic call per new thread for bucket/reason/handoff, deterministic domain-matching (reused from S4) for voice_mode/voice_why. Board screen wired to real data for the first time.
- **S6** — Draft generation and tone controls. The triage Anthropic call (`triage.py`) now also emits a voice-matched `draft` in the same request (voice_mode is computed deterministically *before* the LLM call now, so its traits/notes can be folded into the same prompt — avoids a second sequential LLM call per synced message, which would have compounded the S9-flagged sync-latency concern). New `backend/app/services/tone.py` does the Shorter/Warmer/Firmer rewrite (forced tool-use, same pattern as `voice.py`/`triage.py`) — its prompt explicitly demands a rewrite "genuinely, noticeably different" from the input, because the model would otherwise sometimes return an already-warm draft unchanged on `warmer`. Three new routes on `threads.py`: `PATCH .../draft`, `POST .../tone` (409 if thread isn't `board`/`withEA`/`readyToSend`), `POST .../revert` (409 on an empty `version_stack`). Frontend's draft textarea/tone buttons/revert arrow — built ahead of the backend with a `setTimeout` + static `TONE_DATA` dummy map keyed by non-real seed IDs — are now wired to real calls; `TONE_DATA`/`toneData()`/`ToneData` deleted as dead code.
- **S7** — Real Send/Archive/Skip across all 3 accounts. Send's confirm-dialog + undo toast (backend existed since S2) is now actually wired into the frontend, which had stayed a client-state-only stub the whole time. Archive is new: `backend/app/services/gmail.py`'s `archive_thread` (`users().threads().modify(..., body={"removeLabelIds": ["INBOX"]})` — thread-level, not per-message, since no per-message Gmail id is stored anywhere and a thread's `_id` *is* its `gmail_thread_id`) plus a `dispatch_archive` background task mirroring `dispatch_send` exactly, sharing the renamed `UNDO_WINDOW_SECONDS` constant; `undo_thread` needed **zero changes** since it was already generic over `pending_action`. Skip is new too: immediate, no Gmail call, and deliberately **no undo toast** — the PRD text says the 10-15s undo toast is only for "Send and Archive," so `skipEmail` passes `showUndo: false` (same as the existing Handoff toast). Verified for real, not just via curl: independently re-queried live Gmail state for all 3 accounts after the fact (a one-off scratchpad script using the app's own stored OAuth creds, since the connected Gmail MCP tool only has access to `kevmcg22@gmail.com`) — confirmed archived messages lost `INBOX` but stayed recoverable, skipped messages were completely untouched, and sent replies landed as real `SENT` messages correctly threaded with the `Re:` prefix. All testing used self-directed test threads created for the purpose — the real personal/business mail already sitting on the board (tax questions, PO orders, "Duke Security Review," etc.) was never touched.
- **S8** — Handoff loop, **expanded mid-sprint** past the original PRD scope after a real product conversation. Originally just: `POST .../handoff` (exec-only, sets `withEA`), `POST .../mark-ready` (ea-only, sets `readyToSend` — now with a **real Anthropic-generated** `eaChangeSummary` diffing `draftAtHandoff` against the final draft, short-circuiting to "Reviewed as-is — no changes." with zero LLM latency when nothing changed, new `backend/app/services/handoff.py`). Mid-build, the user pointed out the PRD's "no assistant sending" descope didn't match how an EA relationship actually works — an EA often just finishes the job. After discussion (mechanism: same connected account, no separate EA identity; explicitly deferred reply-all/CC to S9), landed on: once a thread is `withEA`, the EA can *also* send/archive/skip it directly, their judgment per thread, alongside the original mark-ready loop-back. Implemented as an **additive** relaxation — `send_thread`/`archive_thread_route`/`skip_thread` moved from `Depends(require_exec)` to `Depends(require_role)` plus a new `_check_actionable(role, status, exec_statuses)` helper branching by role; `undo_thread` needed **zero changes** (already role-generic). Also added mutual read-only monitoring — Exec's "With EA" nav tag is now a clickable link into the EA queue (was static text), EA gets a brand-new "Ready to send" link — neither grants new authority, `DetailScreen`'s existing per-role/per-status action gating (`showSend`/`showArchiveSkip`/`showMarkReady`) already makes the "wrong" role's view naturally read-only once split correctly. Verified with the same rigor as S7: real audit-log actor attribution (Theo Banks for EA-direct actions vs Mara Lindqvist for handoff/mark-ready), independently re-queried Gmail state confirming EA-direct-send/archive actually happened, and a real undo-after-EA-send test confirming it reverts to `withEA` (not `board`) — proving `undo_thread`'s generic `prev_status` logic needed no S8-specific change at all.
- **S9** — Two-way Gmail sync and reply-all/CC, picked from a 5-candidate scoping conversation at the end of S8 (the other 3 candidates went to S10 — see below). Sync migrated from S5's one-directional date-based `after:` query to Gmail's **History API** (`backend/app/services/gmail.py`'s `get_history`/`get_current_history_id`), with a `history_id` cursor per account that all 3 existing accounts picked up automatically on their first post-S9 sync (no manual migration). `triage.py`'s `sync_account_board` now branches on History records into three paths: brand-new inbox threads (unchanged `_ingest_new_thread` logic), a genuinely new message on an already-tracked thread (`_resync_existing_thread` — re-triages from scratch per product decision, resetting status to `board` **regardless of the thread's current status**, not just "mid-triage" ones), and a real delete/trash (`_mark_deleted_in_gmail` — archives it in Emptify). Sync-triggered changes are attributed to a new `"Emptify Sync"` audit actor (`sync_reclassify`/`sync_archive` actions) rather than Mara/Theo. A real anti-loop fix was required for correctness, not just a nice-to-have: `dispatch_send` now appends the message it just sent into the thread's own `messages` array (tagged with its Gmail message id), so `_resync_existing_thread` can tell "Emptify's own send rippling through History" apart from a genuine new message — without it, every send would falsely reopen its own thread. Reply-all/CC: `Cc` is now parsed off inbound messages (`email.utils.getaddresses`, not regex) into a thread-level `cc_emails` default, threaded through `send_thread`'s new `SendBody`, `dispatch_send`, and the confirm-send dialog (now editable, pre-filled, default-on per product decision). Verified live end-to-end using self-directed Gmail test threads (never real mail) — see "Bugs found and fixed" below for the one real bug this surfaced.

## Bugs found and fixed along the way

Worth knowing so they don't get re-discovered from scratch:

1. **Account slug collision** — account IDs were derived from just the email's local part; `kevin@ember.new` and `kevin@ripplin.org` both slugged to `kevin` and silently overwrote each other. Fixed: slug from the full address.
2. **PKCE `code_verifier` lost between requests** — `google-auth-oauthlib` generates a PKCE verifier tied to the `Flow` instance that built the authorize URL; a fresh `Flow` for the callback request didn't have it, causing `invalid_grant: Missing code verifier`. Fixed: stash the verifier server-side keyed by OAuth `state` between the two requests (`gmail.py`'s `_pending_verifiers`).
3. **CSS class name collision** — a custom `.text-muted` class silently lost to Tailwind's auto-generated `.text-muted` utility (from the theme's "muted" *surface* color, not meant for text) every time, since Tailwind's utility layer outranks `@layer components` regardless of source order. No amount of contrast tweaking had any visible effect until this was found. Fixed: renamed to `.text-emptify-muted` across all 19 usages.
4. **`ACCOUNT_LABELS` hardcoded demo map** — `board-screen.tsx`, `detail-screen.tsx`, `queue-screen.tsx`, `ready-screen.tsx` all looked up account display names from a static 3-entry map (`kestrel`/`northwind`/`personal`) instead of using `EmailThread.accountLabel`, which was already on the object. Real accounts would've shown `undefined`. Fixed across all 4 files; the map is deleted.
5. **Account filter not URL-persisted** — the board's account filter reset to "All accounts" on every refresh because only `screen` was synced to the URL, not `accountFilter`. Fixed: both now round-trip through the URL together.
6. **No loading feedback during sync** — `GET /threads?status=board` does a real, potentially slow (backlog-dependent) sync inline before responding; with zero loading indicator this looked broken/stuck. Fixed: a "Syncing…" label now shows on the board while the fetch is in flight.
7. Decorative "blueprint" corner registration marks on cards were removed per user feedback (pure CSS, `.blueprint > .corner { display: none; }`) — not a bug, but a design change worth knowing about if it looks like something's "missing" from the original SnapDev scaffold.
8. **Gmail's own draft-cleanup misread as a real delete** — S9's two-way sync initially treated *any* `messagesDeleted` History record as a genuine deletion. But replying through Gmail's own UI/API creates a transient `DRAFT` message object that gets deleted the moment the reply actually sends, which shows up as a `messagesDeleted` event too. Result: every direct-Gmail reply was incorrectly archiving the thread instead of re-triaging it — found by live-testing with the Gmail MCP connector's `reply` tool, not by inspection. Fixed (`triage.py`, commit `521ae71`): skip `messagesDeleted` events whose message still carries the `DRAFT` label.

## Conventions established (follow these for S6+)

- **Workflow per sprint:** `EnterPlanMode` → explore relevant existing code → write context + design to the plan file → `AskUserQuestion` for any real product-behavior forks (there's usually at least one per sprint) → `ExitPlanMode` → implement → verify for real (curl the API directly, check Mongo state, hit real Gmail/Anthropic — don't just trust that code compiles) → hand off browser-only steps (OAuth consent, visual checks) to the user → fix anything that surfaces → `git status`/diff review → commit with a real explanatory message → push.
- **API response shape:** backend Mongo documents are snake_case; every response is hand-mapped to the frontend's camelCase `EmailThread`/`Account`/`VoiceProfile` shapes in the router (`_to_response`/`_thread_response` helper functions) — no Pydantic alias magic beyond request bodies.
- **Mutating routes** attach `X-Role` via `require_role`/`require_exec`/`require_ea` (`backend/app/api/v1/deps.py`); GET routes don't require it.
- **Blocking calls** (Gmail API via `googleapiclient`, Anthropic SDK) are always wrapped in `asyncio.to_thread` — see any `_*_sync` / async wrapper pair in `gmail.py`, `voice.py`, `triage.py`.
- **Frontend debounce pattern** for any user-typed field that triggers a PATCH: update local state immediately, debounce the network call via a per-key `setTimeout` ref (see `updateDomains`/`updateNotes` in `emptify-app.tsx`).
- **Manual test scripts** get written to the scratchpad, never committed — see how S2's seed-thread script and various one-off DB-inspection snippets were handled.
- Both dev servers: backend `cd backend && source .venv/bin/activate && uvicorn app.main:app --port 8000`; frontend `cd frontend && npm run dev`.

## Starting point for S10

Nothing here is scoped, prioritized, or committed to — this is the candidate list as of the end of S9, mirrored from `Backend-dev-plan.md`'s S10 section (kept current there; check it for the authoritative version). **The first move, same as every sprint before it, is a real product conversation** — what actually matters enough to build now, in what order, and whether anything below has changed since this was written. Don't start implementing from this list without that conversation first.

1. **OAuth tokens stored as plaintext strings** in Mongo (`backend/app/models/account.py`) — a known, explicit simplification since S2 under the PRD's no-hardening-in-v1 stance. More relevant now that hosting/sharing beyond a local single-user tool is on the table.
2. **No CSRF `state` verification on the OAuth callback** (`backend/app/api/v1/accounts.py`) — Google round-trips `state` but nothing checks it against anything, since there's no session store. Same "might host it" motivation as above.
3. **CORS wide open** (`backend/app/main.py`, `allow_origin_regex=".*"`, commit `cffd9db`) — deliberately loosened mid-S9 by a different collaborating engineer for their own access, not part of this build's own sprint work. Being kept intentionally for now; worth tightening back to an explicit allowlist once that access is no longer needed.
4. **Sequential per-message sync classification** (`triage.py`'s `sync_account_board` — one real Gmail fetch + one real Claude call per new/touched thread, in a loop, capped at 20/account/call). A backlog of a dozen-plus new messages can take over a minute; the S5 "Syncing…" label makes that visible but doesn't make it faster. Candidate fix: parallelize with `asyncio.gather` over a small batch — only worth it if backlogs turn out to be common in practice.
5. **Dev-server hygiene.** Nothing currently detects a stale `uvicorn` process already squatting on port 8000 from a prior session — a new session's dev server can silently fail to bind while the old one keeps answering requests, so testing looks fine but is actually hitting stale code. Cost real debugging time during S9 verification. Worth a lightweight fix (startup port check, or just a documented restart step).

None of these are ranked against each other — that ranking, and whether anything's missing from the list, is exactly what the S10 scoping conversation is for.
